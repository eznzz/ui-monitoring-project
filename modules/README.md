# Monitoring Project · первичные экраны (UI-only)

Все рабочие экраны находятся **в отдельном каталоге `modules/`**, эталонная библиотека `components/` и токены `tokens/` не изменяются.

## Экранный маршрут

1. [Вход](auth/login.html) — выбор платформы или компании исключительно для демонстрационного перехода (не реальная авторизация).
2. [Platform Admin](platform/index.html) — организация списка компаний, просмотр выбранной компании, создание компаний с **типом объектов**, вкладки **Подписка и модули** и **Лицензионные ключи**.
3. [Company Admin](tenant/index.html) — вкладки **Пользователи** (роли `office` и `vessel`), **Суда** и **Лицензии**.
4. [Ship Particulars](tenant/vessel.html) — отдельный редактор карточки судна по разделам исходного документа с 96 обычными полями, редактируемыми грузовыми помещениями и тремя отдельными итогами.

## Справочник типов объектов

Создание компании включает обязательный выбор **типа объектов из Dropdown (Select)**. Список отображается из центрального mock-справочника `MP.OBJECT_TYPES` в [shared/app.js](shared/app.js), отражающего будущий справочник `platform_db`. Сейчас есть **только `vessels`**. Состав типов задаёт платформа, компания не добавляет их самостоятельно. Это **не** лицензируемый модуль, а базовый тип данных, который предприятие может вести на старте.

## Первичная настройка компании

На первом этапе у компании есть только:
- создание пользователя с ролью **office** или **vessel**; для роли **vessel обязательно выбрать конкретное ранее созданное судно**; пароль и подтверждение пароля присутствуют в форме, но **не сохраняются** в публичном демо и не обеспечивают вход;
- добавление и редактирование карточки судна, если platform назначила тип объектов `vessels`.

Нельзя включить отдельные модули из tenant-интерфейса. В демонстрационном UI платформа **сама** отмечает оплату и подтверждает подключение модулей Core, Auth, Documents, Crewing, Supply, VMS, Performance, Reports и Sync. Правило лицензирования: **оплата на платформе → выдача ключа с датой окончания → ввод ключа компанией → запрос с датой → подтверждение платформой**. Администратор компании может лишь запросить подключение, не активировать его.

## Ship Particulars

Источник для набора полей — загруженный пользователем документ `Marta Reefer_Ship_Particulars.docx` (2 страницы). Подробный [список разделов, правил и особенностей данных](tenant/SHIP_PARTICULARS_FIELDS.md).

В публичный демо-репозиторий перенесены **только названия полей и структура**, не фактические контакты и сведения о конкретном судне. В форме не объединены расходящиеся цифры `Total Cargo Volume` и `TOTAL CBM` из исходника.

## Локальные mock-данные

Единый файл `shared/app.js` хранит демонстрационные `companies`, `objectTypes`, `modules`, `tenants`, `users`, `vessels` и записи `licenses` / `licenseRequests` в `localStorage` (`mp-ui-prototype-v1`). Предусмотрена миграция прежней структуры карточек судов и роль `office` по умолчанию для ранее созданных пользователей.

Это **не настоящие базы** `platform_db` и `tenant_db_000001`, не платёжный механизм и не система контроля доступа. Не вводите реальные пароли, контактные или коммерчески конфиденциальные данные.

## Responsive

- В Platform Admin: компании как список, отдельное рабочее пространство выбранной компании, вкладки вместо всех разделов одновременно.
- В Company Admin: основной контент переключается между пользователями и судами, формы пользователей открываются в диалоге, судно заполняется на отдельной странице.
- В Ship Particulars: компактная навигация по разделам, двухколоночные поля на больших экранах, одна колонка на мобильных; грузовые помещения отображаются таблицей на desktop и карточками на mobile.

## Проверка

Проверить вручную в GitHub Pages: создать компанию с `vessels`; открыть её; сначала создать судно, затем пользователя `vessel` с обязательной привязкой к этому судну; проверить пароль и подтверждение без сохранения учётных данных; открыть Ship Particulars; заполнить Ship's Name, IMO, несколько остальных полей, добавить 1A–4C, сохранить и повторно открыть; на платформе отметить оплату модуля, выпустить ключ с датой окончания, ввести его на стороне компании, проверить статус «Ожидает», одобрить запрос на платформе, затем отозвать ключ и проверить прекращение доступа. Проверить переключение тем и ширины 320–1440 px.

Фактические браузерные тесты на физических устройствах ещё необходимы.

## Новые UI-контроли

- **Ship's Type** — Select (Reefer, Bulk Carrier, Tanker, Container Ship, General Cargo, Ro-Ro, Passenger, Fishing, Gas Carrier, Offshore, Tug, Other); исторические значения карточек сохраняются при редактировании.
- **Compartments** — кнопка «Удалить» остаётся в пределах строки таблицы и мобильной карточки; на desktop таблица прокручивается по горизонтали.
- **Licensing** — прототипные ключи создаются только на платформе, содержат даты выпуска и окончания. Запрос и решение имеют собственные даты. Это **не настоящие лицензии и не механизм защиты**: все данные видны в `localStorage`.

## Главные страницы административных кабинетов

По умолчанию `modules/platform/` и `modules/tenant/` открывают **Dashboard** с информационными плитками, а не формы и таблицы. Боковое меню и плитки ведут в **уже существующие** разделы, не создавая дубликатов:

- Platform: Главная (`#dashboard`), Компании (`#companies`), Подписка и модули (`#modules`), Лицензионные ключи (`#keys`), Правила подключения (`#principles`).
- Company: Главная (`#dashboard`), Пользователи (`#users`), Суда (`#vessels`, когда разрешены platform), Лицензии и запросы (`#licenses`).
- На главных страницах оставлены только плитки разделов с краткими счётчиками и ссылками. Отдельный блок `mp-dashboard-summary` удалён в обоих кабинетах как дублирующий информацию.
- Данные плиток читаются из общего mock-состояния, обновляются после действий на той же странице и после изменения данных в другой вкладке браузера.
- Маршруты реализованы хешами в рамках существующих страниц, поэтому ссылки работают без дополнительных правил GitHub Pages.

## Грузовые помещения: единый адаптивный вид без scrollbar

Исходная широкая таблица помещений больше **не создаётся**. Каждое помещение отображается полноценной карточкой с восемью редактируемыми полями и кнопкой удаления. Карточки перестраиваются по доступной ширине, не требуют горизонтальной прокрутки ни на desktop, ни на mobile. Структура хранения `holds[]`, идентификаторы полей и функциональность добавления шаблона 1A–4C сохранены.

## Обязательное использование исходного Dashboard Template

Текущий UI платформы, компании и Ship Particulars **не определяет собственную альтернативу** Sidebar/Topbar/User Menu. Их разметка и названия классов повторяют [корневой Dashboard Template](../index.html): `app`, `sidebar`, `sidebar__logo`, `sidebar__nav`, `topbar`, `user-menu`, `content`. Все рабочие страницы подключают оригинальные [`style.css`](../style.css) и [`script.js`](../script.js) непосредственно, а также [`tokens/tokens.css`](../tokens/tokens.css).

Порядок подключения стилей:
1. `tokens/tokens.css` — единые токены.
2. `style.css` в корне — оригинальные Sidebar/Topbar/User Menu/Button/Field и адаптивная боковая навигация.
3. `modules/shared/ui.css` — только предметные формы, таблицы, карточки и dashboards.
4. `modules/shared/template.css` — локальная совместимость контейнеров `mp-*` с эталонной оболочкой.

`script.js` из корня обеспечивает мобильное меню, пользовательский dropdown и переключение Light/Dark в административных экранах. `modules/shared/app.js` отвечает только за mock-состояние, настройки и компоненты не входящие в базовую оболочку. В Login используется оригинальная карточка `content__card`, поля `form-row`, кнопка `btn`, цветовая система и логотип шаблона; вход не имеет Sidebar по смыслу сценария.

Старые `mp-shell`/`mp-sidebar` и их собственный JS мобильного меню больше не используются в новых административных HTML-страницах. Существующие маршруты, демоданные и логика лицензирования не меняются.

## Поправки UI: модальные окна и единые иконки

- Нативные окна `<dialog>` для создания компании и пользователя теперь используют центрирование, внутреннюю вертикальную прокрутку и ограничение высоты viewport. Это исправляет конфликт с глобальным сбросом `margin: 0` в корневом `style.css`.
- Для закрытия доступны Escape, «Отмена» и кнопка-крестик в заголовке. Модальные окна используют `modules/shared/template.css` и не изменяют CSS исходного Dashboard.
- При создании компании **тип объекта выбирается только из одного выпадающего списка**. Варианты динамически формируются из справочника `MP.OBJECT_TYPES` в `modules/shared/app.js` (сейчас только Vessels). В данных сохраняется массив `objectTypes` для совместимости с существующим прототипом.
- Все иконки навигации, плиток dashboards и информационных блоков используют **Font Awesome Free 6.5.2** с существующего CDN, как и оригинальный Dashboard Template.
- Локальная проверка компоновки модального окна в Chromium при ширинах 320, 375, 390, 768 и 1440 CSS px прошла. Проверка реального Safari/iPhone остаётся отдельной задачей.

## Административные операции и плотность интерфейсов

Обновлены рабочие экраны `platform/index.html` и `tenant/index.html`:

- **Создание компании:** ручной «Код компании» (`COMP-001`) удалён — это была необязательная UI-метка, а не системный идентификатор. Платформа автоматически назначает `tenant_db_00000N` и не переиспользует номер после удаления. Из старых локальных записей код удаляется при нормализации; имя компании и тип объекта сохраняются.
- **Удаление компании:** доступно суперадминистратору из панели выбранной компании. Обязательное подтверждение предупреждает о количестве пользователей, судов, ключей и запросов. После подтверждения удаляются сама компания, её `tenant`-данные, лицензии и запросы.
- **Удаление пользователя:** доступно в реестре компании, работает с идентификатором пользователя. Связь пользователя `vessel` с судном удаляется вместе с пользователем.
- **Удаление судна:** доступно из реестра судов с подтверждением. Если к IMO привязаны аккаунты роли `vessel`, удаление блокируется, пока эти аккаунты не будут удалены. Так не остаются невалидные назначения.
- **Общие подтверждения:** `modules/shared/confirm.js` формирует модальное окно в стиле исходного шаблона с действиями «Отмена» и «Удалить».
- **Размеры:** административный контент занимает всю доступную ширину, без искусственного ограничения до 1310px; внутренние отступы и промежутки между блоками уменьшены; экран Ship Particulars использует ту же широкую компоновку.
- **KPI и информационные плитки:** теперь компактнее, с меньшими числовыми показателями и спокойными отступами; переходы к основным функциям визуально приоритетнее статистики.

Эти операции изменяют **только mock-состояние браузера в localStorage**, а не настоящие `platform_db` / `tenant_db_*`. Подтверждённое удаление в демо не имеет корзины и восстановления. В реальной системе потребуются API, разграничение полномочий, журнал аудита и отдельно согласованная политика архивации/удаления.

## Исправление высоты KPI и единая геометрия заголовков

Обнаружена причина «гигантских» `.mp-dashboard-stat`: базовый `.content` растягивается по высоте через `flex:1`, а `.mp-main-content` одновременно использует CSS Grid. Без `align-content:start` неявные строки Grid растягивали `.mp-dashboard-head` и `.mp-dashboard-summary` на всю свободную высоту экрана. Уменьшение padding самих KPI не устраняло причину.

В `modules/shared/template.css` закреплено:
- `align-content:start`, `grid-auto-rows:max-content` для `mp-main-content`, Dashboard и рабочих областей;
- `grid-auto-rows:max-content` для блока статистики;
- общие отступы, межэлементные промежутки, размер заголовка и высота строки для `.mp-dashboard-head` и `.mp-page-head`;
- единые правила на Platform Admin, Company Admin и Ship Particulars. Эталонный корневой шаблон не изменён.

В локальном Chromium-воспроизведении CSS Grid при 1440×900 и 1440×1200 высота статистической карточки оставалась ~37–38 CSS px, без зависимости от высоты окна. Проверены также ширины 320, 390, 768 и 1024 CSS px без горизонтального переполнения. Эта проверка моделирует существенные правила размещения; для подтверждения опубликованной страницы и iOS Safari нужна отдельная визуальная приёмка.

## Экран входа: возвращена двухколоночная компоновка

`modules/auth/login.html` снова использует исходный левый блок с заголовком «Одна платформа. Разные уровни доступа.» и описанием разделения уровня платформы и компании. Справа находится форма в отдельной карточке `content__card` на фоновом токене `--vms-color-canvas`, который соответствует выбранной Light/Dark теме; сама карточка использует `--vms-color-surface`.

Правила компоновки вынесены только в `modules/auth/login.css`. При ширине до 900 px обе панели становятся вертикальными, чтобы поля формы не сжимались. Сохраняются исходные `tokens/tokens.css`, `style.css` и демонстрационные переходы из `login.js`. UI остаётся без реальной аутентификации.
