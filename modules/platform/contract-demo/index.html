Отдельная Tenant область. API: /api/v1/tenant-admin/users и /api/v1/company — не Platform JWT.

Только демонстрационные данные
Изоляция Tenant

Это не кросс-tenant статистика Central Platform. В реальной системе пользователи, роли и доступные модули запрашиваются из Tenant Runtime с отдельной авторизацией и разрешениями.

Активация и Provisioning

Режим чтения: GET /companies?status=provisioning → GET /companies/{tenantID}/provisioning. Нет запуска C01.

Компании в provisioning

Без повторного запуска

Состояние C01, receipts и timeline здесь только фикстуры. Подтверждение Reviewer не создаёт Tenant DB и не доказывает готовность маршрута.

Заявки на активацию

GET /activation-reviews · отдельное право tenant.provision.approve. Одобрение требует другого Reviewer, свежих пароля и TOTP на реальном сервере.

0

В концепте решение имитируется без ввода пароля или TOTP, без серверного provisioning и без выдачи реальной лицензии.

Reviewer · приглашения и подтверждение

Контракт: GET /reviewers/status, GET/POST /reviewers/invitations, GET /reviewers/invitations/{requestID}/status и /owner-confirm. Все операции ниже — mock, без секретов и отправки e-mail.

Не проверено

Перед повторной отправкой приглашения проверяйте состояние запроса и почтовый ящик. Не создавайте новый запрос, пока не выяснено состояние прежней попытки.

Реальный POST требует пароль Owner и свежий TOTP, которых публичный прототип не запрашивает. Запрос приглашения сам по себе не отправляет письмо.

Защищённые действия

Реальное изменение шаблона, запись SMTP-пароля и отправка приглашения требуют свежие Owner password/TOTP. Секреты здесь НЕ вводятся; реальная почта НЕ отправляется.

Почтовый сервер · LAB

GET /mail/settings и POST /mail/diagnostics доступны только при включённом feature flag. В демо — безопасная имитация без SMTP-соединения.

Проверка не выполнялась

HTTP 200 не гарантирует успешной доставки: в ответе отдельно проверяются status и stage. Никаких реальных e-mail из макета не отправляется.

Мониторинг служб Central Node

GET /system/services: read-only состояние доверенных IPC, без проверки отправки SMTP или готовности Provisioning.

Не выполнялась

Границы и источники

Визуальная модель создана для согласования API-ориентированного пользовательского опыта. Это не новая реализация аутентификации, не backend и не работающий контроль доступа.

Разделение API

Platform API: /internal/platform-admin/*; Tenant API: отдельное пространство /api/v1/*.

Права доступа

Только сервер определяет permissions. В этом макете роли — выбираемые тестовые фикстуры.

Создание компании

Создание компании: requestId UUID v4 + code + name. Здесь нет ввода владельца или objectType — их нет в данном POST.

Редактирование черновика

Редактирование только draft с expectedRevision; 409 требует повторного чтения.

Активация и Reviewer

Заявка на активацию не означает, что компания provisioned или active. Reviewer — отдельный сценарий с серверным MFA.

Секреты и безопасность

Никаких реальных паролей, TOTP, токенов и секретов в localStorage или fixtures.

Демо не вызывает API. Документация: Central Platform API · Матрица соответствия (если принята в main).
