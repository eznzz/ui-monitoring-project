# Central Platform — контрактный UI-прототип

[Открыть концепт](index.html) · отдельный изолированный интерфейс в `modules/platform/contract-demo/`.

## Назначение

Макет для согласования Platform Login, просмотра/создания/редактирования компаний и подачи/рассмотрения заявок. Используется **исключительно HTML/CSS/JS** и дизайн-система Monitoring Project. Старый `modules/platform/index.html` и Tenant UI не затронуты.

Основа: [Platform API](https://github.com/developerpiter/vdms/blob/docs/central-platform-api/docs/api/central-platform.md) и клиент [Central Workspace](https://github.com/developerpiter/vdms/blob/main/web/central-workspace/src/api.ts). Этот макет **не отправляет HTTP-запросы**, не выполняет реальную аутентификацию или provisioning, не принимает пароль/TOTP и не сохраняет секреты. Состояние фикстур существует только в оперативной памяти вкладки и сбрасывается при обновлении.

## Сценарии

1. Вход: выберите фикстуру Owner / Reader / Reviewer и успешный либо ошибочный ответ, имитируйте `POST /login → POST /access → GET /me`. Состояние сессии не гарантирует реального доступа.
2. Реестр: фильтры по статусу, клиентский поиск по текущему mock-выводу, cursor-подобная пагинация, просмотр карточки. Доступ определяется выбранными fixture permissions.
3. Новая компания: только `requestId`, `code`, `name` (UUID создаётся макетом), результат `draft`; в запросе нет выбранного objectType, e-mail владельца или tenant DB имени.
4. Редактирование: только `draft` и `tenant.draft.update`; ревизия увеличивается; есть кнопка имитации 409.
5. Активация: запрос с `requestId` и `expectedRevision`, отдельная очередь Reviewer и отказ в self-approval. Решение демонстрационное, не активирует физическую базу данных. Сценарий approve/reject в реальности требует MFA, проверок backend и конфигурации стенда.

## Ограничения

- Права Reader, Owner, Reviewer — **тестовые фикстуры**, не буквальные роли из API. В реальном клиенте permissions приходят из `GET /me`.
- Mock-пагинация и поиск в браузере не являются заявкой на наличие полнотекстового поиска в API.
- Доступность approve/reject зависит от SQL-предпосылок и feature flags на стенде. Статус заявки `approved` не означает `active` или завершённый C01 provisioning.
- Ошибки 401/403/409/503 показываются как варианты UX; реальные серверные ответы могут быть plain text.
- Этот прототип не должен использовать реальные персональные данные, пароли, TOTP или защищённые токены.
- Для будущей React-миграции экранные модели и фикстуры проверяются повторно против зафиксированной ревизии VDMS API.

## Приёмочные сценарии

- Reader: просмотр списка без возможности создания/редактирования.
- Owner: создание draft и редактирование с revision; симуляция 409.
- Owner: запрос на активацию; запрет самостоятельно одобрить собственную заявку.
- Reviewer: отдельный просмотр очереди и имитация решения.
- 401/503: экран ошибки входа без демонстрации ложной сессии.
- Смена темы, узкая ширина, клавиатурная навигация.

## Reviewer и аудит: второй UI-инкремент

- Экран `#reviewer`: статусы `GET /reviewers/status` и приглашения `requested → queued → sent → claimed`, имитация подтверждения Owner. Изменение mock-статуса **не является** реальной отправкой письма или выполнением Claim; реальный backend требует операторы, MFA, соответствующие permission и отдельные подтверждения.
- Экран `#logs`: mock `GET /platform-logs?limit&offset`, только тестовый Platform Owner с нужными правами. Фильтр категории выполняется локально исключительно для просмотра.
- Просмотр истории решений доступен тестовому Reviewer, исторические решения в макете показываются только как фикстуры.
- Пароли, TOTP, email-токены не собираются. В форме Reviewer допускаются только адреса `@example.test`.

Внимание: этот прототип проверяет **UI сценарии**, а не реальные SQL permissions, защиту API или состояние операторов Central Node.


## Визуальная база (строгое соответствие, обновление 2026-11-23)

Эталон зафиксирован по ветке [docs/vdms-ui-api-mapping-20261123](https://github.com/eznzz/ui-monitoring-project/tree/docs/vdms-ui-api-mapping-20261123):
- [components](https://github.com/eznzz/ui-monitoring-project/tree/docs/vdms-ui-api-mapping-20261123/components): типографика, цвета, поля, кнопки, таблицы, состояния, модальные окна.
- [modules](https://github.com/eznzz/ui-monitoring-project/tree/docs/vdms-ui-api-mapping-20261123/modules): Login, Platform Admin, общий Dashboard Template.
- `tokens/tokens.css`, `style.css`, `modules/shared/ui.css`, `modules/shared/template.css`, `script.js`: общие реализации.

**В интерфейсе не допускается отдельная дизайн-система.** `concept.css` удалён. Главный вход использует `mp-login mp-login--split` и `modules/auth/login.css`. Рабочие экраны используют исходные `sidebar`, `topbar`, `user-menu`, `mp-card`, `mp-basic-table`, `mp-btn`, `mp-field`, `mp-dialog`. Responsive и тема обслуживаются штатными правилами, а не вторым контроллером.

### Разделение ответственности

Соблюдение эталонной **визуальной системы** не означает, что прежний mock-компонент `modules/platform/index.html` имеет действующий серверный контракт для лицензий, object types или владельца. Логика и разрешения новых экранов берутся из VDMS API. Различия фиксируются отдельно; не следует возвращать неподтверждённые операции ради визуального совпадения.

### Проверки перед утверждением

1. Chromium smoke tests: форма Login, стандартная оболочка Platform, компании, Reviewer, журнал, меню мобильной версии, входные ограничения и ошибки.
2. Тёмная и светлая темы; размеры desktop/mobile; отсутствие неиспользуемых собственных системных стилей.
3. Ручная визуальная проверка и сравнение с `components/` и `modules/` обязательны сверх успешных функциональных тестов.
