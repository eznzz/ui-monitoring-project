# Monitoring Project — etalon_db, Platform и Tenant

**Статус:** согласованная логическая архитектура (13.10.2026). **Не является** подтверждением наличия этих подсистем в исходниках VDMS, физической схемой PostgreSQL, спецификацией миграций или утверждённым HTTP API.

Связанные решения: [DECISIONS.md](DECISIONS.md), [AUTH_AND_ROUTING.md](AUTH_AND_ROUTING.md), [VESSELS_AND_SCOPES.md](VESSELS_AND_SCOPES.md), [SHIP_PARTICULARS_AND_USER_ASSIGNMENTS.md](SHIP_PARTICULARS_AND_USER_ASSIGNMENTS.md).

## 1. Три уровня и их ответственность — согласовано

| Уровень | Назначение | Чего не делает |
| --- | --- | --- |
| `etalon_db` | **Поэтапно формируемый и развиваемый эталон нужной структуры Tenant**: общая основа и определения специализации по Object Type, начиная с `vessels`; источник эталонных структур для подготовки Tenant. | Не служит рабочим хранилищем судов, пользователей и документов отдельных компаний. Не является эталоном CSS/дизайн-системы. |
| `platform_db` | Реестр компаний и их Tenant, платформа и владельцы, лицензии/подписки; **Super Admin выбирает для создаваемой компании Object Type**, доступный из эталонных определений. Platform связывает компанию с её рабочим Tenant через доверенный backend. | Не хранит собственные копии Ship Particulars каждого Tenant и не определяет независимо схему всех типов объектов. |
| `tenant_db_XXXXXX` | **Отдельная рабочая БД компании**, подготовленная на основе нужной эталонной структуры для выбранного Object Type; реальные объекты, пользователи Tenant, RBAC, назначения, история и модульные данные. | Не является общим каталогом типов объектов для всех компаний и не управляет физическим развёртыванием чужих Tenant. |

**Главная цепочка:** `etalon_db (эталон структуры + Object Type) → platform_db (создание компании, выбор типа) → tenant_db (рабочая структура и данные компании)`.

Под «формированием из эталона» пока понимается **логический результат**: созданный Tenant должен иметь соответствующую согласованную структуру. Способ реализации в PostgreSQL (миграции, DDL, подготовленные шаблоны или сочетание), частота обновления и границы специализированных схем не выбираются frontend-командой.

## 2. Поэтапное развитие эталона — согласованный принцип

- `etalon_db` развивается поэтапно по мере определения **необходимой структуры** Tenant, а не считается полностью готовой БД всех будущих предметных областей.
- Общие для типов объектов механизмы (авторизация/права, реестр объектов, связи и история — состав подлежит сверке с VDMS) **концептуально отделяются** от предметных структур.
- На текущем этапе разрабатывается Object Type **`vessels`**. Для него требуются Ship Particulars и связанные судовые данные по уже согласованным требованиям. `trucks`, `bikes` и другие типы — **будущие расширения**, а не функции, уже реализованные в backend/UI.
- Объектный тип выбирается при создании компании. **Нынешний демонстрационный сценарий предполагает один выбранный тип**; поддержка нескольких типов у одной компании и возможность изменить тип после создания остаются отдельными вопросами.
- Структура/данные одной компании изолированы от других: действует ранее согласованный принцип **одна компания — отдельная tenant-БД**.
- **Эталон не копирует реальные данные других Tenant.** Судно компании получает собственный постоянный ID и находится в её реестре; IMO и Ship Particulars — характеристики конкретного судна.

## 3. Создание компании — согласованная функциональная последовательность

1. Super Admin в Platform Admin начинает создание компании и указывает данные компании и e-mail первого Company Owner.
2. Platform UI **через доверенный API** получает перечень доступных Object Types, определяемых эталонной моделью, и позволяет выбрать нужный тип, сейчас `vessels`.
3. Backend проверяет платформенные полномочия и валидность выбранного типа, создаёт/регистрирует компанию, исходного владельца и **отдельный Tenant с необходимой структурой на основе `etalon_db`**.
4. После успешного серверного результата Platform сохраняет связь компании, Object Type и Tenant; пользователь продолжает работу уже в своём tenant-контексте.
5. Tenant создаёт реальные объекты выбранного типа в своём реестре; для нового `vessels` применяются согласованные правила **Ship's Name + IMO обязательны, стартовый статус `inactive`**.

Это **логическая последовательность**. Фактические транзакционные границы, операции provisioning, поведение при частичном сбое, повторная попытка, время выполнения, eventual consistency и контракты ответов требуют решения API-команды. Frontend не объявляет Tenant созданным до подтверждения сервера.

## 4. Разделение Object Type и Object — согласовано

- **Object Type** — эталонное определение класса объектов (`vessels`, впоследствии `trucks`, `bikes`), выбранного компанией через Platform.
- **Object** — отдельный рабочий экземпляр в Tenant (конкретное судно, грузовик и т. п.), с постоянным ID, принадлежностью компании, статусом и предметными данными.
- **Ship Particulars** — предметная часть Object Type `vessels`; она остаётся внутри Tenant, не в Platform и не в эталонной рабочей таблице.
- Уровень Object Type **не равен оплачиваемому модулю**: модульные подписки и права доступа управляются отдельно. Будущую совместимость модулей с типами объектов ещё необходимо согласовать.
- `objects` в терминах VDMS и `vessels` в UI должны быть сопоставлены **по фактической API/БД-модели**: нельзя заранее считать, что `objectID`, `vesselId` и `IMO` являются одним ключом.

## 5. Правила для frontend и демонстрации

**Согласовано:** эталонный Dashboard Template, глобальная дизайн-система, `tokens/`, `components/` и визуальная оболочка **не изменяются**. Browser UI не читает `etalon_db`, `platform_db` и `tenant_db` напрямую, не запускает SQL, не выбирает имена физических БД и не формирует их на стороне клиента.

**Предлагается на этапе будущей интеграции, а не утверждённый API-контракт:**
- Получать доступные Object Types для Platform Admin через адаптер Platform API; в демо использовать безопасный статический mock-каталог, помеченный как mock.
- При создании компании показывать состояние серверной подготовки Tenant: «создаётся», «готов», «ошибка», «повторить» — только если API подтвердит соответствующий процесс и статусы.
- Отображать в карточке компании выбранный Object Type; версию эталона можно показывать **только если** backend решит её учитывать и предоставит.
- Для Vessels после подготовки Tenant открывать существующие экраны судового реестра и Ship Particulars, не меняя базовый шаблон.
- Не передавать параметры физической БД в клиентские URL и не давать пользователю произвольно подменять объектный тип внутри уже созданной компании.

**Текущий UI-прототип:** `modules/shared/app.js` содержит `MP.OBJECT_TYPES` как mock-справочник Platform; физическое происхождение каталога из `etalon_db` в нём ещё не реализовано. `modules/auth/`, `modules/platform/`, `modules/tenant/` не изменяются этим архитектурным решением.

## 6. Что требует проверки с VDMS API/DB — НЕ согласованный контракт

1. Где и как физически представлены Object Types и поэтапно создаваемые эталонные структуры в `etalon_db`; кто публикует допустимые типы для Platform API.
2. Какой набор общих/специализированных структур устанавливается в Tenant на каждом этапе; могут ли миграции добавлять новые структуры без удаления данных.
3. Как backend выполняет provisioning tenant-БД по эталону, фиксирует результат, обрабатывает частичные ошибки, повторные запросы, откаты и безопасность.
4. Нужна ли версия/ревизия эталона для конкретного Tenant; если да, как её хранить и мигрировать ранее созданные Tenant без автоматического разрушительного изменения.
5. Как универсальная объектная модель VDMS соотносится с предметными объектами Vessels и их атрибутами, статусами, назначениями и объектным RBAC.
6. Какие поля и статусы API возвращает на этапах выбора Object Type и создания компании/tenant; в каком виде отражается долгий процесс provisioning.
7. Какие дополнительные Object Types и комбинации типов в одной компании будут поддерживаться в будущем.

**Безопасность:** не изменять рабочую `tenant_db_000001`, не модифицировать проверенные миграции PostgreSQL 1–29 и не проводить интеграционные опыты с действующими Tenant. Это ограничения из предоставленного контекста VDMS; фактический backend и актуальное состояние его ветки остаются непроверенными. Все изменения БД и миграций — в зоне ответственности backend.

## 7. Граница утверждения

**Согласована логическая модель `etalon_db → platform_db → tenant_db` и поэтапное формирование эталона.** Не утверждены SQL-структуры, готовность существующего VDMS API, endpoint-имена, форматы ответов, алгоритм копирования/сборки Tenant, статус миграций и возможность клонирования физических PostgreSQL-баз.
