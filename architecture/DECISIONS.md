# Monitoring Project — согласованные архитектурные правила

**Статус:** проектирование frontend v0.1 · 13.10.2026.
**Источник:** явно согласованные проектные требования; физическая схема БД и формат API находятся в ответственности другого отдела.

## A. Согласовано

### A1. Границы ответственности

- Наша команда разрабатывает **только frontend**: экраны, дизайн-компоненты, навигацию, хранение frontend-состояния, обращения к API и отображение ответов.
- Структуру БД, backend и реальные API предоставляет **другой отдел**.
- Физические имена баз используются в этих документах для архитектурного понимания, но не для прямого обращения из браузера.

### A2. Platform и Tenant

- Центральная структура: `platform_db → platform → companies, tenants, licenses, modules, subscriptions, tenant_connections, platform_users`.
- **Одна компания — одна отдельная `tenant_db`.**
- Пример структуры tenant: `tenant_db_000001 → core, auth, documents, crewing, supply, vms, performance, reports, sync`.
- Ship Particulars и связи пользователей с судами хранятся **внутри tenant_db**.
- Frontend взаимодействует с **API конкретных модулей**: запрос → ответ через API.

### A3. Пользователи и единый вход

- `platform_users` — пользователи **только** двух административных категорий: суперадминистраторы платформы и администраторы компаний.
- Пользователи компании (например, будущие `office` и `vessel`) находятся **в отдельной таблице в `tenant_db.auth`**, а не в `platform_users`.
- Для **обеих категорий пользователей одна страница входа**.
- **E-mail глобально уникален во всей системе Monitoring Project**: адрес не может повторяться между `platform_users`, любыми `tenant_db_*.auth` или внутри одного из источников. Один адрес соответствует **одному аккаунту**.
- При регистрации/изменении e-mail проверка уникальности должна охватывать **все источники пользователей**. Обеспечение этой гарантии при конкурентных запросах — обязанность backend/БД другого отдела; проверка во frontend может быть только предварительной.
- Правило «единая форма» **не** означает объединение учётных записей или таблиц БД; источник учётной записи определяет серверная аутентификация.

### A4. Лицензирование и подписки

- **License** — право на покупку/использование системы (точная модель юридического права, статусов и срока требует API-контракта).
- **Subscription** — подписка на отдельный функциональный модуль.
- `licenses` и `subscriptions` — разные предметные сущности, их нельзя считать синонимами.
- Нынешняя демонстрационная механика «ключ на каждый модуль» — **временная UI-имитация, не утверждённое правило будущей системы**.

## B. Предлагается frontend (не согласованный контракт)

- Сервер определяет единственную учётную запись по глобально уникальному e-mail, а затем возвращает её источник, идентичность, разрешения и разрешённый tenant-контекст; frontend строит начальный маршрут по этим данным. Реализация поиска и способ проверки уникальности не определены.
- Пользователь **не выбирает роль** на настоящей форме входа (в старом демо переключатель нужен исключительно для тестового перехода).
- Маршруты для суперадмина, администратора компании и сотрудников компании защищаются единым механизмом проверки сессии и разрешений.
- Разрешения и модульные подписки используются для показа меню и экранов, но конечные проверки права доступа выполняются API.
- Под API заводятся frontend service adapters, чтобы сменить mock-провайдер на реальный backend без переписывания UI.

См. подробный черновик в [AUTH_AND_ROUTING.md](AUTH_AND_ROUTING.md).

## C. Требует согласования с другим отделом

1. Каким способом единый Auth API находит аккаунт в `platform_users` или конкретной `tenant.auth` по глобально уникальному e-mail? Каким образом backend гарантирует уникальность между физически раздельными БД и при одновременном создании/изменении аккаунтов?
2. Может ли один глобально уникальный аккаунт администратора компании иметь доступ к нескольким компаниям/tenant-контекстам при правиле «одна компания — одна БД»?
3. Какие атрибуты сессии, идентификаторы разрешений, статусы пользователя и назначенные суда возвращает API?
4. Какая модель сессии выбрана (HttpOnly Cookie или другой согласованный способ), как реализуются обновление/завершение сессии и защита от CSRF?
5. Какими API возвращаются лицензия на систему, подписки на модули, сроки действия, статусы оплаты и границы доступа?
6. В каком модуле находится API Ship Particulars, какое поле служит устойчивым ID судна, как выглядят связи с `tenant.auth`?
7. Будут ли разные API-hosts для модулей, общий API gateway, отдельные scopes и как выполняется tenant routing **без выдачи клиенту секретов БД**?
8. Как обрабатываются попытки регистрации или смены e-mail на уже занятый адрес? Считать ли адреса с разным регистром одним адресом (рекомендуемая политика) и какие правила нормализации подтверждает backend?
9. Какие ошибки и состояния обязательны для frontend: 401, 403, 404, недоступный tenant, истекшая лицензия, выключенный модуль, просроченная подписка?

## D. Сохранение текущего UI-прототипа

- Демонстрационные `modules/auth/login.html`, `modules/platform/` и `modules/tenant/` **не меняем** в ходе архитектурного проектирования.
- В демо ещё есть условный выбор роли, localStorage и устаревшие для будущей архитектуры ключи по модулям. Это **известные отличия**, а не изменения согласованных требований.
- Дизайн-система остаётся в корневых файлах и `docs/`; текущие проектные решения — в `architecture/`.
