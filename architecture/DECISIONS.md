# Monitoring Project — согласованные архитектурные правила

**Статус:** проектирование frontend v0.1 · 13.10.2026.
**Источник:** явно согласованные проектные требования; физическая схема БД и формат API находятся в ответственности другого отдела.

## A. Согласовано

### A1. Границы ответственности

- Наша команда разрабатывает **только frontend**: экраны, дизайн-компоненты, навигацию, хранение frontend-состояния, обращения к API и отображение ответов.
- Структуру БД, backend и реальные API предоставляет **другой отдел**.
- Физические имена баз используются в этих документах для архитектурного понимания, но не для прямого обращения из браузера.

### A2. Platform и Tenant

- Центральная структура: `platform_db → platform → companies, tenants, licenses, modules, subscriptions, tenant_connections, platform_users`.
- **Одна компания — одна отдельная `tenant_db`.**
- **Только Super Admin создаёт новую компанию через Platform UI и указывает e-mail её первого владельца.** При создании backend должен зарегистрировать компанию и первоначального владельца в `platform_db.platform.platform_users`, связать их с отдельной физической tenant-БД и обеспечить глобальную уникальность e-mail. Company Owner, Tenant Admin, Office и Vessel **не могут создавать компании**. Конкретная форма, способ первичного установления пароля, provisioning и API-контракт остаются на согласовании с backend; браузер сам БД не создаёт.
- **В Platform UI Super Admin может архивировать компанию, но не может окончательно её удалить.** Архивирование сохраняет компанию, исходного владельца, связанные аккаунты, отдельную tenant-БД и данные, историю, лицензии и подписки. **Ручное окончательное удаление на уровне backend — отдельная операция другого отдела** и не представляется кнопкой, пользовательским сценарием или API-операцией удаления через Platform UI. Архивация отличается от временной блокировки; влияет ли она на пользовательский вход, текущие сессии, работу модулей и можно ли восстановить компанию из архива — пока **не утверждено**. Предлагается статус «Архивирована» с серверным подтверждением и аудитом действия.
- **Super Admin обладает максимально широкими административными полномочиями на уровне всей платформы** (высшая платформенная роль), редактирует основные реквизиты **любой компании** (название, адрес, телефон, контакты) и **может из собственного кабинета Platform Admin выбрать любую компанию и управлять её пользователями, дополнительными администраторами, судами и рабочими данными с полномочиями Company Owner**. Он при этом **остаётся Super Admin**, не становится владельцем и не входит в чужой аккаунт: первоначальный owner ID, роль владельца и привязка компании остаются неизменными. Все действия идут через API с серверной проверкой прав/tenant-контекста и аудитом действительного исполнителя и компании. Системные ID и связь с tenant-БД не редактируются как обычные реквизиты; e-mail владельца меняется через ранее утверждённую отдельную процедуру. «Максимальные полномочия» не отменяют запрета передачи владения и самостоятельной смены e-mail Super Admin. Доступ Super Admin к данным и функциям модулей **не ограничен статусом подписки выбранной компании** (см. A4); управление типами объектов и другие необратимые операции требуют отдельных решений/API-контрактов; **в Platform UI компания может быть только архивирована, окончательное удаление выполняется исключительно вручную на уровне backend**; **временная блокировка/разблокировка компании и отдельных её модулей Super Admin уже согласована** (см. A4); frontend не подключается к БД напрямую.
- Пример структуры tenant: `tenant_db_000001 → core, auth, documents, crewing, supply, vms, performance, reports, sync`.
- Ship Particulars и связи пользователей с судами хранятся **внутри tenant_db**.
- Frontend взаимодействует с **API конкретных модулей**: запрос → ответ через API.

### A3. Пользователи и единый вход

- `platform_users` содержит суперадминистраторов платформы и **первых администраторов — владельцев компаний**. При создании компании формируется её первый аккаунт администратора (**владелец компании**); он хранится в `platform_db.platform.platform_users`.
- **В одной компании допускается несколько администраторов.** Все **дополнительные (обычные) администраторы** этой компании хранятся в `tenant_db.auth`, а не в `platform_users`. В `tenant_db.auth` также хранятся остальные пользователи компании (например, `office` и `vessel`).
- **Каждый аккаунт администратора компании (`company_owner` / `tenant_admin`) закреплён за одной компанией и одной `tenant_db`.** Несколько разных аккаунтов администраторов могут управлять одной компанией; **только отдельная платформенная роль Super Admin** может выбирать любую компанию для администрирования из Platform UI. Это не назначение Super Admin администратором компании и не передача владельческих прав на его аккаунт.
- Два типа администраторов компании — **владелец** (первый аккаунт в `platform_users`) и **обычный администратор** (дополнительные аккаунты в `tenant.auth`). Это согласованные категории, но **не утверждённые буквальные коды ролей в API**. Принципиальное разделение прав зафиксировано ниже, а конкретные идентификаторы разрешений предстоит согласовать с API.
- Для **обеих категорий пользователей одна страница входа**.
- **E-mail глобально уникален во всей системе Monitoring Project**: адрес не может повторяться между `platform_users`, любыми `tenant_db_*.auth` или внутри одного из источников. Один адрес соответствует **одному аккаунту**.
- При регистрации/изменении e-mail проверка уникальности должна охватывать **все источники пользователей**. Обеспечение этой гарантии при конкурентных запросах — обязанность backend/БД другого отдела; проверка во frontend может быть только предварительной.
- Правило «единая форма» **не** означает объединение учётных записей или таблиц БД; источник учётной записи определяет серверная аутентификация.
- **Пользователи `tenant.auth` категорий Tenant Admin, Office и Vessel вправе самостоятельно менять e-mail только собственного аккаунта** через «Мой аккаунт» (отдельно от изменения e-mail владельца в `platform_users`). Сервер сохраняет тот же ID, роль, компанию и привязки к судам и проверяет глобальную уникальность адреса по всем БД. **Суперадминистратор платформы не имеет права самостоятельно менять e-mail своего аккаунта через «Мой аккаунт»**: поле только для чтения, API должен отклонять self-service смену для этой роли. Этот запрет не касается уже согласованного ручного изменения e-mail **владельца компании** через Platform UI. Порядок подтверждения изменения для `tenant.auth` требует API-согласования.
- **Все пользователи без исключения — Superadmin, Company Owner, Tenant Admin, Office и Vessel — могут самостоятельно менять пароль собственного аккаунта в разделе «Мой аккаунт».** Обязательно ввести **текущий пароль** и **новый пароль**; сервер должен проверить текущий пароль и действующую сессию до изменения. Отдельное подтверждение **не требуется**: нет повторного ввода нового пароля, подтверждающего письма/кода и согласования администратором. **После успешного изменения пароля текущая сессия остаётся действующей; автоматического выхода и повторного входа нет. Все остальные активные сессии того же аккаунта должны быть отозваны сервером**, в том числе на других устройствах/браузерах, где потребуется повторный вход с новым паролем. Требования к сложности и технический механизм отзыва сессий — на согласование с командой API. Право менять пароли других пользователей из этого правила не возникает.

### A3.1. Разделение прав владельца и обычного администратора — согласовано

- **Владелец компании** имеет полный **административный доступ в пределах своей компании**, включая создание и управление дополнительными администраторами (аккаунты в `tenant.auth`), обычными пользователями, судами и рабочими данными.
- **Super Admin вправе выполнять административные действия уровня владельца в любой компании**, выбранной через его собственный Platform Admin. Это особое межкомпанейское платформенное полномочие, а не второй владелец, логин от имени владельца или расширение прав обычных администраторов. Tenant-данные открываются и изменяются только через соответствующий API, с авторизацией и аудитом.
- **Обычные администраторы** управляют **обычными пользователями**, судами и рабочими данными своей компании в рамках выданных полномочий, но **не управляют владельцем компании** и **не управляют учётными записями других администраторов**.
- Полный доступ владельца **не означает** права суперадминистратора платформы и не расширяет доступ за пределы собственной компании.
- **Отсутствие действующей подписки на платный модуль ограничивает доступ к нему для пользователей компании**, включая Company Owner, Tenant Admin, Office и Vessel. **Исключение — Super Admin платформы:** в контексте любой выбранной компании он имеет полный административный доступ к данным и функциям всех модулей через API, **даже если подписка этой компании на модуль неактивна или отсутствует**. Это не активирует подписку, не меняет её статус и не открывает модуль пользователям компании. Доступ к фактически несуществующим данным/неразвёрнутому модулю определяется реальной доступностью API и данных. Принцип разграничения license/subscription сохраняется; правила изменения/приобретения подписок отдельно **не утверждены**.
- Одно административное рабочее пространство допускается для двух типов администраторов, но действия и разделы frontend показываются **по разрешениям, подтверждённым API**. Скрытие кнопки во frontend не заменяет серверную проверку.

**Не определено:** отдельные разрешения API, правила управления лицензией/подписками, конкретные действия с профилями и системными настройками. **Передача статуса владельца не предусмотрена**.

### A3.2. Неизменяемое владение и восстановление доступа владельца — согласовано

- **Передача права владения компанией не предусмотрена.** Нельзя назначить нового владельца из дополнительных администраторов, поменять владельца через кабинет компании или реализовать workflow передачи прав.
- Первый администратор — **владелец компании** — продолжает храниться в `platform_users`, как и было определено при создании компании.
- **Суперадминистратор платформы должен иметь возможность инициировать смену (сброс) пароля владельца компании** через интерфейс управления этой компанией на платформе. Владелец получает защищённую ссылку и **самостоятельно устанавливает новый пароль**; суперадминистратор его не видит. Изменение пароля не изменяет владельца, e-mail, компанию или источник учётной записи.
- **Два согласованных способа смены e-mail владельца компании:** (1) **суперадминистратор платформы жёстко и вручную заменяет адрес** через Platform Admin → карточка компании; после успешного ответа API новый адрес сразу становится логином **без обязательного подтверждения ссылкой или старой почтой**; (2) **владелец самостоятельно меняет свой e-mail** в настройках собственного аккаунта в Company Admin. Оба способа сохраняют **тот же серверный ID владельца, компанию, роль и источник `platform_users`**, не являются передачей права владения.
- Дополнительные администраторы компании и пользователи `tenant.auth` **не могут сбрасывать пароль или менять e-mail владельца**. Владелец вправе изменять **свой собственный** e-mail, но не статус владения компанией.
- Новый e-mail должен пройти **обязательную глобальную проверку уникальности** среди `platform_users` и всех `tenant.auth` через API. **Подтверждение нового адреса по ссылке не является обязательным условием** ни для ручной смены суперадмином, ни для смены владельцем в своём аккаунте. Ни в одном варианте доступ к прежнему ящику не требуется по умолчанию. Дополнительные способы защиты (например, повторное подтверждение текущей сессии, журналирование или уведомления) согласуются с отделом API/безопасности, без изменения этих бизнес-правил.
- **Сброс забытого пароля владельца** остаётся отдельным процессом: платформа инициирует защищённую ссылку, владелец самостоятельно устанавливает новый пароль. **Самостоятельная смена известного пароля** через «Мой аккаунт» доступна всем категориям с обязательной проверкой **старого пароля**, без отдельного подтверждения, как указано в A3. **Смена e-mail — непосредственная операция обновления существующей учётной записи** через API, доступная суперадмину вручную или самому владельцу в своём профиле. Не требуется обязательного письма с подтверждением, очереди ожидания подтверждения или доступа к прежнему ящику. Контракт API, проверка прав, аудит, возможное уведомление и политика действующих сессий — на согласование с отделом API/безопасности. Frontend не показывает существующий пароль и не получает его из API.

### A4. Лицензирование и подписки

- **License** — право на покупку/использование системы (точная модель юридического права, статусов и срока требует API-контракта).
- **Subscription** — подписка на отдельный функциональный модуль. **Статус подписки ограничивает пользователей компании, но не блокирует служебный доступ Super Admin к любому модулю в любой компании.** Backend определяет статус подписки отдельно от платформенного административного разрешения; оба должны учитываться при выдаче прав.
- **Согласована временная блокировка компании Super Admin:** только Super Admin вправе запретить доступ **всем пользователям конкретной компании**, включая Company Owner, Tenant Admin, Office и Vessel, и впоследствии снять запрет. Компания, её tenant, пользователи и данные сохраняются. **Сам Super Admin сохраняет полный доступ**, в том числе для устранения причин блокировки. Доступ при активных сессиях и прямых запросах к API должен блокироваться на сервере. После разблокировки действуют прежние проверки системной лицензии, подписок и разрешений.
- **Согласована отдельная временная блокировка подключаемого модуля конкретной компании Super Admin:** заблокированный модуль недоступен пользователям этой компании **даже при действующей подписке**, другие модули остаются доступны по собственным подпискам/ролям (если компания не заблокирована целиком). **Super Admin сохраняет доступ к данным и функциям модуля.** Разблокировка возвращает обычные проверки подписок и разрешений.
- **Административные блокировки обратимы и независимы от коммерческих статусов:** они **не удаляют данные, не приостанавливают и не продлевают лицензию/подписку, не меняют оплату** и не передают права владения. **Для блокировки как всей компании, так и конкретного её модуля согласованы оба режима: (1) без срока — до ручного снятия Super Admin; (2) до заданных Super Admin даты и времени — с автоматическим серверным снятием в установленный момент. В обоих режимах Super Admin может снять блокировку вручную раньше.** Снятие одной блокировки не снимает независимо установленную блокировку другого уровня: разблокировка компании оставляет возможные блокировки модулей, и наоборот. Запланированная разблокировка должна срабатывать на backend без открытого браузера; досрочное ручное снятие отменяет ожидаемое автоматическое действие. Сведения о блокировках/исключительных действиях и автоматическом снятии доступны frontend через API с аудитом Super Admin и target company/module. Точные имена статусов, формат даты/часового пояса, реализация автоматического снятия, уведомления и судьба действующих сессий — на согласование с backend. Глобальная остановка модуля во всех компаниях данным решением не установлена.
- `licenses` и `subscriptions` — разные предметные сущности, их нельзя считать синонимами.
- Нынешняя демонстрационная механика «ключ на каждый модуль» — **временная UI-имитация, не утверждённое правило будущей системы**.

## B. Предлагается frontend (не согласованный контракт)

- Сервер определяет единственную учётную запись по глобально уникальному e-mail, а затем возвращает её источник, идентичность, разрешения и разрешённый tenant-контекст; frontend строит начальный маршрут по этим данным. **И владелец компании из `platform_users`, и дополнительные администраторы из `tenant.auth` должны попадать в кабинет единственной закреплённой компании**, с меню и действиями согласно серверным правам, без выбора компании. Реализация поиска и способ проверки уникальности не определены.
- Пользователь **не выбирает роль** на настоящей форме входа (в старом демо переключатель нужен исключительно для тестового перехода).
- Маршруты для суперадмина, администратора компании и сотрудников компании защищаются единым механизмом проверки сессии и разрешений.
- Frontend следует согласованному разграничению: владелец видит управление дополнительными администраторами, обычный администратор — только управление обычными пользователями, судами и рабочими данными. **У суперадминистратора платформы в карточке компании должны быть отдельные операции сброса пароля и ручной немедленной смены e-mail владельца**, а **у владельца — редактирование собственного e-mail в настройках аккаунта**; все без передачи статуса владельца. Детали и доступность действий определяются серверными `permissions`. Разрешения и модульные подписки используются для показа меню и экранов, но конечные проверки права доступа выполняются API.
- Под API заводятся frontend service adapters, чтобы сменить mock-провайдер на реальный backend без переписывания UI.

См. подробный черновик в [AUTH_AND_ROUTING.md](AUTH_AND_ROUTING.md).

## C. Требует согласования с другим отделом

1. Каким способом единый Auth API находит аккаунт в `platform_users` или конкретной `tenant.auth` по глобально уникальному e-mail? Каким образом backend гарантирует уникальность между физически раздельными БД и при одновременном создании/изменении аккаунтов?
2. В каком поле и каким образом Auth API возвращает единственную назначенную компанию (`companyId`) и tenant-контекст **для первого и дополнительных администраторов**? Как frontend узнаёт об отзыве доступа?
3. Какие атрибуты сессии, идентификаторы разрешений, статусы пользователя и назначенные суда возвращает API? **Согласовано:** текущий пароль обязателен и сервер проверяет его перед сохранением нового. **Согласовано:** после успеха пользователь остаётся в текущей авторизованной сессии, без перенаправления на Login. **Согласовано:** все остальные активные сессии данного аккаунта отзываются после успешной смены пароля; текущая сохраняется. **На согласование:** как именно валидируется новый пароль, как сервер отзывает остальные сессии/токены и выдаёт ответ об успешном завершении операции? Отдельного подтверждения смены пароля нет.
4. Какая модель сессии выбрана (HttpOnly Cookie или другой согласованный способ), как реализуются обновление/завершение сессии и защита от CSRF?
5. Какими API возвращаются лицензия на систему, подписки на модули, сроки действия, статусы оплаты и границы доступа?
6. В каком модуле находится API Ship Particulars, какое поле служит устойчивым ID судна, как выглядят связи с `tenant.auth`?
7. Будут ли разные API-hosts для модулей, общий API gateway, отдельные scopes и как выполняется tenant routing **без выдачи клиенту секретов БД**?
8. Как обрабатываются попытки регистрации или смены e-mail на уже занятый адрес? Считать ли адреса с разным регистром одним адресом (рекомендуемая политика) и какие правила нормализации подтверждает backend?
9. Какие ошибки и состояния обязательны для frontend: 401, 403, 404, недоступный tenant, истекшая лицензия, выключенный модуль, просроченная подписка, **административная блокировка компании или отдельного модуля Super Admin** и **архивирование компании**? **Согласовано:** блокировки не отменяют подписку и не ограничивают Super Admin; архивирование не удаляет tenant/данные. **Открыто:** меняет ли статус архива сам доступ пользователей и их текущие сессии.
10. **Зафиксировано:** управлять дополнительными администраторами может владелец, обычные администраторы — нет. **Уточнить для API:** какие операции доступны при управлении аккаунтами (создание, блокировка, удаление, восстановление) и как проверяются права и ограничения? Кто управляет системной лицензией и модульными подписками?
11. **Согласовано:** передача статуса владельца запрещена; пароль сбрасывается суперадмином по защищённой ссылке; e-mail меняется **немедленно после успешного API-ответа**, вручную суперадмином **или самим владельцем в профиле**, без обязательных ссылок подтверждения. **Требует API-согласования:** идентификаторы операций, защита от несанкционированных изменений, атомарная глобальная уникальность, аудит, уведомления и политика сессий; отдельно определить порядок блокировки/удаления недоступного владельца без передачи статуса.

## D. Сохранение текущего UI-прототипа

- Демонстрационные `modules/auth/login.html`, `modules/platform/` и `modules/tenant/` **не меняем** в ходе архитектурного проектирования.
- В демо ещё есть условный выбор роли, localStorage и устаревшие для будущей архитектуры ключи по модулям. Это **известные отличия**, а не изменения согласованных требований.
- Дизайн-система остаётся в корневых файлах и `docs/`; текущие проектные решения — в `architecture/`.
