# Monitoring Project — реестр судов, активная группа и границы модулей

**Статус:** согласованная бизнес-модель статусов судов, работа с активной группой и делегирование выбора судов; названия полей, API и технические детали — предложения frontend, 13.10.2026.

Связанные материалы: [DECISIONS.md](DECISIONS.md), [PERMISSIONS_MATRIX.md](PERMISSIONS_MATRIX.md), [AUTH_AND_ROUTING.md](AUTH_AND_ROUTING.md), [LICENSING_AND_SUBSCRIPTIONS.md](LICENSING_AND_SUBSCRIPTIONS.md).

## 1. Единый реестр компании и три состояния судна — согласовано

Каждая компания располагает **единым реестром судов**, включая их **Ship Particulars**. Судно имеет постоянный серверный ID и принадлежит только своему tenant. Рабочие модули **не содержат собственные независимые копии списка судов**; они используют серверный контекст активных судов компании и назначений по модулю.

| Статус | Где видно | Работа в модулях |
| --- | --- | --- |
| **Активное / включённое** | В основном списке «Суда» / Ship Particulars | Может участвовать в Мониторинге, Документах, Crewing, Supply и прочих модулях **только** при действующем модуле, назначении судна и разрешениях пользователя |
| **Неактивное / выключенное** | **Остаётся в обычном разделе «Суда»**, с явной меткой «Неактивно» и фильтром | **Исключается из обычных рабочих экранов всех остальных модулей**, списков, селекторов, показателей по активному флоту, новых рабочих операций |
| **Архивное** | Сохраняется в реестре, но показывается в отдельном **«Архив судов»** или фильтре архивных | **Исключается из обычной работы и рабочих экранов всех остальных модулей**, не допускает новых операций |

**Согласовано:** неактивное судно не удалено и не спрятано из реестра судов, но **не должно отображаться** в других модулях, включая Мониторинг и Документы. Архивное судно тоже не входит в рабочие наборы и хранится отдельно в реестре. Перевод в любое из двух состояний **не удаляет** Ship Particulars, документы, мониторинговую историю, связи, события, аудит или прочие уже сохранённые данные.

**Неактивность ≠ архивирование ≠ удаление.** Архив — длительное выведение из рабочего реестра, неактивность — сохранение в общем списке при выключении из работы. Физическое удаление судна как business operation **этим решением не утверждается**.

## 2. Активная группа судов — основной рабочий контекст

**Система выполняет текущую работу только с активной (включённой) группой судов компании.** Это единый серверный набор:
- `companyActiveVessels` = суда tenant со статусом **active**.
- `moduleVessels(company, module)` = **подмножество** `companyActiveVessels`, которое Company Owner / уполномоченный Tenant Admin назначили выбранному **подключённому модулю** и которое укладывается в ручной лимит Super Admin.
- `userModuleVessels` = `moduleVessels`, дополнительно ограниченное персональными правами пользователя и назначениями на суда. **Office и Vessel получают только назначенные им активные суда** в конкретном модуле, даже если компания имеет свободный лимит; не получают права просмотра всего флота через прямой API-запрос.

**Эффективный scope** для обычных пользователей при работе модуля: `companyActiveVessels ∩ moduleAssignment ∩ userAssignment`, **плюс** действующие системная лицензия и модульная подписка (даты), отсутствие архива/блокировок компании и модуля. Если судно inactive или archived, его **нет** в рабочем scope даже при прежнем назначении. Для Super Admin сохраняется глобальный административный доступ к данным и архивам из собственного Platform Admin — не подмена обычного рабочего контекста компании.

- По умолчанию Мониторинг, Документы, отчёты, рабочие реестры, выбор судна, агрегированные показатели и операции синхронизации **по текущему флоту** строятся **только из активных судов, доступных текущему модулю и пользователю**. Неактивные/архивные не добавляются обратно локальным кешем, параметром URL, селектором или прямым API-вызовом.
- Исторические данные не уничтожаются; **специальные режимы просмотра истории** судна должны быть отдельными авторизованными административными/архивными маршрутами и **не возвращать** судно в обычную работу модулей. Конкретный способ чтения истории через модульные API — отдельное API-решение.
- Переключение active → inactive/archived **немедленно исключает** судно из рабочих API-наборов/операций даже в уже открытой сессии. Frontend после успешного API-ответа обновляет списки, открытые контексты, показатели и селекторы; backend продолжает проверять scope при каждом защищённом запросе.
- В реестре судов допускаются фильтры **«Активные», «Неактивные», «Архив»** и поиск. **Архив** — отдельный фильтр/вкладка, не обычный рабочий список.

## 3. Кто управляет статусом и распределением судов

**Согласовано:** Company Owner своей компании и уполномоченный Tenant Admin (в пределах прав) могут создавать/редактировать Ship Particulars и менять состояние судна; они **распределяют активные суда по доступным модулям** в пределах ограничений подписок, установленных Super Admin. **Super Admin** из собственного Platform Admin может выполнять эти действия для любой выбранной компании с аудитом реального исполнителя. Office/Vessel не получают управление реестром или статусом по умолчанию; могут видеть только назначенные **активные** суда и работать с ними по правам.

| Операция | Company Owner | Tenant Admin | Super Admin |
| --- | --- | --- | --- |
| Создавать/редактировать Ship Particulars | Да, своя компания | Да, в пределах разрешений | Да, любая выбранная компания |
| Активировать / сделать судно неактивным | Да, при проверке мест во всех назначенных модулях | По выданным правам, при проверке мест | Да, с серверной проверкой мест |
| Архивировать судно | Да | По выданным правам | Да |
| Восстановить из архива **в `inactive`** | Предлагается: да | Предлагается: по выданным правам | Предлагается: да |
| Назначать активные суда в модуль / исключать из него | Да, **в пределах лимита и активных подписок** | По выданным правам и в пределах лимита | Да; изменение коммерческих лимитов — его отдельная операция |
| Установить/изменить `vesselCap`, даты и статус коммерческой подписки | **Нет** | **Нет** | **Да, вручную** |

**Согласовано: архивное судно восстанавливается только в статус `inactive`**, не возвращаясь сразу в рабочие модули. Затем уполномоченный администратор отдельным действием переводит его в `active`, а backend предварительно проверяет наличие свободных мест в каждом модуле с сохранёнными назначениями. **Возвращать архивное судно сразу в `active` или автоматически восстанавливать модульную видимость нельзя.** Конкретное распределение прав на операцию «Восстановить из архива» предлагается дать Company Owner / Tenant Admin с разрешением на управление флотом / Super Admin, но имя permission и API-контракт нужно утвердить с backend.

## 4. Лимиты Fleet 3/5/10/30/50/Unlimited и активная группа

По ранее утверждённой тарификации Super Admin **вручную** задаёт для каждой модульной подписки **срок** и **лимит судов**. Owner / Tenant Admin управляют **составом активных судов, реально задействованных в модуле**, без права изменять оплаченный лимит.

**Согласованное правило потребления лимита:**
- **Место в лимите конкретного модуля занимает только судно со статусом `active`, назначенное этому модулю.** Формула занятых мест: `count(distinct activeCompanyVessels ∩ moduleAssignments)`. Судно `inactive` или `archived` **не занимает рабочее место**, даже если его прежняя связь с модулем хранится для истории/восстановления. **Лимиты Fleet проверяются отдельно для каждого модуля**; не складывать назначения разных модулей в один глобальный счётчик.
- Не стирать запомненные назначения и связи при выключении судна; счёт рабочих мест строить только по пересечению назначений с active. **Перед повторным включением** backend **заново проверяет** лимиты всех модулей, к которым судно было назначено. При превышении **операцию включения отклонить без частичного изменения статуса**, показать конфликт и предложить владельцу/администратору изменить набор активных назначений/выключить другое судно либо связаться с коммерческим отделом для изменения Fleet tier вручную через Super Admin. Не назначать оплату/новый лимит автоматически.
- При уменьшении Super Admin ёмкости подписки ниже числа назначенных **активных** судов нельзя автоматически удалять суда или данные: требовать явного выбора и корректировки доступного набора.
- Если подписка отсутствует или истекла, ранее сохранённые назначения **не дают рабочий доступ** и могут сохраняться для последующего восстановления обслуживания. Нет автоматического подключения или продления.

**Согласовано:** считаются **только активные суда, назначенные конкретному модулю**; inactive/archived **освобождают рабочее место в этом модуле**, но не уменьшают автоматически цену, не создают возврат, не продлевают срок подписки и не меняют тариф Super Admin. Точное финансовое оформление и перерасчёты при смене флота остаются за коммерческим отделом, без автоматического возврата средств.

## 5. Предлагаемый frontend и концептуальные API

**Вкладка «Суда»**: фильтры активные/неактивные/архив, карточка Ship Particulars со статусом, действия «Включить», «Сделать неактивным», «Архивировать», список назначений к модулям и индикатор использования ёмкости каждого модуля. Архивное судно не отображать как действующее. Подтверждать массовое исключение из модулей, если судно уже там используется. **Никакого удаления данных.**

**Компания → Модули / Активные суда**: в каждом подключённом модуле показывать только доступные для назначения **активные суда**, лимит и занятые места; Company Owner / Tenant Admin выбирают состав и сохраняют, API решает допустимость и конфликты. Для Office/Vessel возвращать только доступные согласно назначению суда.

**Предлагаемые сервисы — не контракт:**

| Функция | Смысл |
| --- | --- |
| `getCompanyVessels({statuses})` | Список реестра судов с серверными фильтрами и полномочиями |
| `getActiveVesselScope(companyId)` | Единственная активная группа компании для рабочих модулей |
| `setVesselStatus(vesselId,status)` | Управление active/inactive/archived с правами, серверной валидацией и аудитом; перед `inactive → active` проверять места всех подключённых/назначенных модулей; конфликт — запрет без частичных изменений |
| `getModuleVesselScope(companyId,moduleId)` | Активные назначенные суда модуля и серверные лимиты |
| `assignModuleVessels(companyId,moduleId,vesselIds)` | Owner / разрешённый Tenant Admin назначают активные суда без превышения лимита |
| `getAccessibleVessels(moduleId)` | Готовый scope конкретного пользователя для работы модуля |
| `getVesselArchive(vesselId)` | Специальный просмотр сохранённых карточки/истории в административном режиме — предложение |
| `restoreArchivedVessel(vesselId)` | Архив → **`inactive` без автоактивации**; конкретные permissions и API — на согласование |

Backend отвечает за физическую таблицу судов, согласованность статусов со всеми модульными API, tenant routing, проверку ownership и scopes, аудит, запрет операций с inactive/archived из прямых запросов, синхронизацию и изменение текущих сессий. Frontend **не** хранит отдельные несвязанные статусы судна в модулях и не решает доступ только скрытием UI.

## 6. Следующий блок для предметного обсуждения

**Карточка судна, назначение пользователей и группировка флота:** какие поля Ship Particulars обязательны; нужны ли дополнительные пользовательские группы флота помимо автоматически определяемой активной группы; кто назначает Office/Vessel к судам и как назначение связано с модульными permissions; какие права требуются для восстановления архивного судна в `inactive`. **Лимит модулей и правило его освобождения при выключении уже согласованы**. Данные судов и история при любой смене статуса сохраняются.
