# Monitoring Project — Ship Particulars и назначения пользователей судам

**Статус:** согласованная бизнес-модель frontend (13.10.2026). Физическая схема БД, форматы/пути API, коды ролей и разрешений не утверждены и относятся к backend-команде.

Связанные документы: [DECISIONS.md](DECISIONS.md), [VESSELS_AND_SCOPES.md](VESSELS_AND_SCOPES.md), [PERMISSIONS_MATRIX.md](PERMISSIONS_MATRIX.md), [AUTH_AND_ROUTING.md](AUTH_AND_ROUTING.md). Источник состава полей существующего **демо**: [SHIP_PARTICULARS_FIELDS.md](../modules/tenant/SHIP_PARTICULARS_FIELDS.md) и [ship-particulars.js](../modules/tenant/ship-particulars.js).

## 1. Единая карточка Ship Particulars — согласовано

- У каждого судна один постоянный **внутренний серверный ID** в рамках своего tenant и **одна карточка Ship Particulars**; все модули обращаются к этому реестру, а не дублируют собственные карточки/суда.
- **Ровно два обязательных поля при создании судна:** **Ship's Name** (название) и **IMO No.** Все остальные поля, включая MMSI, Call Sign, Flag и Ship's Type, **необязательные** и могут заполняться/уточняться позднее.
- Сохраняем существующий подробный состав из демо: **96 простых полей в 10 разделах**, таблицу/карточки грузовых помещений (8 атрибутов каждой строки) и отдельные итоги \`TOTAL CBM\`, \`TOTAL CBFT\`, \`TOTAL SQM\`. Не заменяем подробную форму сокращённой шестипольной анкетой.
- Разделы: Identification / Registration; Principal Dimensions / Tonnage; Cargo / Reefer; Compartments Capacity and Dimensions; Cargo Gear / Machinery; Speed / Performance; Tank Capacities / Added Fields; Owner / Manager / Operator; Vessel Communications; Additional Fields Recommended for Chartering.
- Не смешиваем \`Total Cargo Volume\` с \`TOTAL CBM\`, а также отдельные строки расхода топлива из исходного документа. Не навязываем без подтверждённого API-контракта преобразование размерностей и текстовых эксплуатационных значений.
- Ship Particulars — базовый tenant-реестр, **не отдельный оплачиваемый модуль**. Рабочие функции Documents, Monitoring и других модулей по-прежнему зависят от их собственных разрешений, активных подписок и назначений.

**Уточнение для API:** формат и проверка IMO (демо проверяет 7 цифр; алгоритм контрольной цифры для production требует серверной спецификации), правило уникальности IMO между компаниями, нормализация/типизация полей и системные ID определяются совместно с backend. Не считаем текущую валидацию демо утверждённым серверным контрактом.

## 2. Статусы и первичное создание — согласовано

| Состояние | Правило |
| --- | --- |
| **Новое судно** | Создаётся **исключительно со статусом \`inactive\`**. Ни создание карточки, ни её заполнение автоматически не включают судно в рабочие модули. |
| \`inactive\` | Остаётся в обычном разделе «Суда» с явной меткой; не участвует в текущих рабочих наборах и не занимает места в Fleet-лимитах модулей. |
| \`active\` | Переводится вручную отдельным действием уполномоченного администратора с серверной проверкой прав и мест **во всех модулях с сохранёнными назначениями**. Доступ к конкретному модулю дополнительно требует его назначения/действующей подписки. |
| \`archived\` | Находится в отдельном архиве/фильтре; данные, ID, Ship Particulars, документы, аудит и назначения сохраняются. |
| Восстановление \`archived\` | Только **в \`inactive\`**; затем отдельная ручная активация в \`active\`. |

**Запрещено:** автоматически делать новое судно \`active\` после сохранения; включать его в рабочий модуль без назначения; переносить \`inactive\`/\`archived\` в пользовательский рабочий scope; удалять данные/назначения при выключении или архивировании.

## 3. Пользователь ↔ судно: множественные назначения — согласовано

- **Связь many-to-many:** один пользователь категории **Office** или **Vessel** может быть назначен **одному или нескольким судам**; у судна может быть несколько назначенных пользователей. **Vessel не ограничен одним судном.**
- **Office** может быть создан без судовых назначений; до назначения и предоставления модульных прав у него нет доступа к судовым данным.
- **Vessel** при создании назначается **не менее чем к одному судну**, с возможностью выбрать несколько. Для нового назначения в обычном рабочем сценарии администратор выбирает активные суда; ранее сохранённые связи с выключенными/архивными судами не стираются. При последующем отзыве всех назначений рабочий судовой scope пользователя становится пустым, но сам аккаунт автоматически не удаляется.
- **Company Owner** вправе создавать/изменять назначения Office/Vessel внутри своей компании. **Tenant Admin** — только при соответствующем разрешении и только обычным пользователям своей компании, без права управлять владельцем и другими администраторами. **Super Admin** делает то же в контексте любой выбранной компании из Platform Admin, не входя под чужой учётной записью.
- Пользователь Office/Vessel **не назначает себе суда**, не повышает свои права и не активирует/архивирует суда по умолчанию. Назначение судна не даёт автоматически права на модуль, изменения Ship Particulars или управление судном.
- Назначения и связь с пользователем хранятся в его tenant-контексте, а не в платформенном списке всех судов. Физический способ хранения и атомарность обновлений определяет backend.

## 4. Эффективный scope рабочих модулей — согласовано

Для Office/Vessel в каждом отдельном модуле применяется пересечение:

\`effectiveVessels(user, module) = activeCompanyVessels ∩ moduleAssignedVessels ∩ userAssignedVessels\`

Кроме принадлежности судна пересечению, необходимы: действующая **системная лицензия**, действующая **подписка на данный модуль**, отсутствие архива/административных блокировок компании и модуля, разрешения пользователя на модуль и на конкретное действие. Если любое условие не соблюдено, рабочий доступ отсутствует.

- Пользователь может видеть **разные подмножества своих судов в разных модулях**; нельзя показывать весь назначенный ему флот в модуле, которому эти суда не выделены.
- **Количество пользователей, назначенных судну, не расходует дополнительные Fleet-места.** Лимит конкретного модуля расходуют только \`active ∩ moduleAssignedVessels\`, независимо от числа Office/Vessel-пользователей.
- Когда судно переводится в \`inactive\`/\`archived\`, назначение пользователю **сохраняется**, но текущий доступ прекращается немедленно, в том числе в открытой сессии и при прямом API-запросе. Изменение разрешений/назначений также должно применяться сервером, а frontend обновляет селекторы, маршруты, списки и текущий контекст.
- Company Owner, уполномоченный Tenant Admin и Super Admin используют свои отдельно проверяемые **административные** полномочия; пользовательская формула Office/Vessel не должна случайно лишать администратора прав управления общим реестром. Для Super Admin сохраняются утверждённые исключения по подпискам и архивным данным.

## 5. История изменений и предлагаемый frontend

**Согласовано на уровне бизнес-требования:** при изменении Ship Particulars, статуса судна и пользовательских назначений нужна прослеживаемая история действий с реальным исполнителем, временем и предметом изменения. Выключение или архивирование судна не уничтожает предыдущие значения и рабочую историю. Детализация полей журнала, срок хранения и API просмотра истории — **не утверждены**.

**Предлагаемое поведение frontend (не готовый UI и не API-контракт):**
- В реестре «Суда» — отдельный статус и явная кнопка **«Включить»** у нового \`inactive\` судна; ошибки проверки Fleet-лимитов отображаются без частичной активации.
- В редакторе Ship Particulars — сохранение неполной карточки с обязательными названием/IMO, секции существующей анкеты, просмотр истории уполномоченным администратором.
- В карточке пользователя Office/Vessel — множественный выбор активных судов, отображение числа назначений и перечня судов, включая отметку неактивных сохранённых связей при редактировании; права на модули показывать отдельно, не смешивать с назначениями.
- Сервер отдаёт **уже авторизованный** набор судов и разрешений; UI не выводит доступ из localStorage, URL, количества назначений или скрытых кнопок.

## 6. Открыто для следующего согласования / API

1. Имена разрешений на просмотр/редактирование Ship Particulars, назначения пользователей, смену статуса, восстановление архива и просмотр истории; точная матрица CRUD внутри рабочих модулей.
2. API/JSON-контракт получения единого судового реестра, сохранения частично заполненных полей, изменений статусов, пакетного назначения нескольких судов и отдачи эффективного scope; ошибки конкурентных изменений/лимитов.
3. Серверная проверка IMO (контрольная цифра, дубликаты, граничные случаи) и единицы/типы расширенных технических характеристик.
4. Формат, аудит, фильтрация и доступность истории для административных и архивных маршрутов.
5. Дополнительные пользовательские группы флота **не вводим в текущую минимальную модель**; их потребность можно рассмотреть отдельным решением, не смешивая с уже утверждённой группой \`active\`.

**Следующий предметный блок:** **права Office/Vessel внутри конкретных модулей (Module Permissions & Navigation)** — роли, операции \`view/create/edit/approve/delete\`, ограничения на уровне судна/модуля и построение меню. После бизнес-матрицы можно согласовать с backend соответствующие permission-коды и API-контракты.

## 7. Граница изменений

Этот документ описывает **будущую frontend-архитектуру**, не реализует её. **Публичный UI-прототип в \`modules/\`, его mock/localStorage и дизайн-система остаются неизменными.**
