# «Мой аккаунт» — проектирование frontend

**Статус:** Draft v0.1 · 13.10.2026. **Согласованные правила помечены отдельно от предложений.** Это спецификация будущего UI, а не готовый экран и не утверждённый HTTP API.

Связанные документы: [согласованные решения](DECISIONS.md), [авторизация и маршрутизация](AUTH_AND_ROUTING.md). Текущие `modules/` и дизайн-система **не меняются**.

## 1. Цель и границы

Раздел **«Мой аккаунт»** предназначен для просмотра и изменения **только собственной** учётной записи текущего авторизованного пользователя. Он доступен из пользовательского меню App Shell и использует один визуальный паттерн для всех категорий:

- `platform_users / superadmin` — суперадминистратор платформы;
- `platform_users / company_owner` — первоначальный администратор, владелец компании;
- `tenant.auth / tenant_admin` — дополнительный администратор компании;
- `tenant.auth / office` — сотрудник компании;
- `tenant.auth / vessel` — пользователь, связанный с судном/судами согласно API.

Коды категорий — **условные названия frontend**, а не утверждённые enum значения API. **Все входят через один Login**; e-mail **глобально уникален** среди всех источников. Один аккаунт администратора привязан к одной компании.

**«Мой аккаунт» ≠ «Управление пользователями»**: изменение чужих ролей, создание дополнительных администраторов, назначение судов, блокировка чужих аккаунтов и платформенное восстановление доступа владельца не помещаются в этот раздел. Они относятся к специализированным административным экранам.

## 2. Согласовано (из проектных решений)

1. **Владелец компании может самостоятельно заменить свой e-mail** в настройках собственного аккаунта. Успешный ответ API означает немедленную смену логина; **письменное подтверждение старого или нового адреса не является обязательным**. Новый адрес должен быть глобально уникальным. ID аккаунта, компания, источник `platform_users` и статус владельца неизменны.
2. **Суперадмин платформы отдельно вручную меняет e-mail владельца** через Platform → карточка компании, **не через свой «Мой аккаунт»**. Это операция над чужим аккаунтом, не передающая статус владельца.
3. **Суперадмин платформы инициирует сброс пароля владельца** по защищённой ссылке; владелец сам устанавливает новый пароль. Эта платформенная операция — не правило для остальных категорий аккаунтов.
4. **Статус владельца не передаётся** другому пользователю. Обычные администраторы не управляют владельцем и другими администраторами.
5. Frontend получает идентичность и права от API и **не определяет источник учётной записи** по email или URL; API проверяет право на каждое действие.
6. Правила самостоятельной смены e-mail и пароля **для остальных типов пользователей** отдельно **не утверждены**.

## 3. Информационная архитектура экрана (предложение frontend)

**Логический будущий маршрут:** `/account` для всех категорий; URL, SPA/MPA и router ещё не утверждены. Ссылка в раскрывающемся User Menu → «Мой аккаунт»; кнопка «Выйти» остаётся отдельным элементом того же меню.

Экран состоит из **трёх компактных секций** (не отдельный интерфейс для каждой роли):

### A. Профиль

- Отображаемое имя — чтение; редактирование всеми категориями **предлагается, не согласовано**.
- E-mail текущего аккаунта — чтение; **редактирование владельцем уже согласовано**; для остальных категорий см. матрицу и открытые вопросы.
- Категория учётной записи (суперадмин / владелец / администратор / Office / Vessel) — **только чтение**, берётся из API.
- Организация — только чтение для всех пользователей компании; для суперадмина вместо компании показывать «Платформа». Информация о физической `tenant_db` не отображается.
- При необходимости аватар/телефон — **опциональное предложение**, не считать поля обязательными до согласования модели данных.

### B. Безопасность

- **«Изменить мой пароль»** — предлагаемое действие для всех вошедших пользователей (например, текущий пароль → новый пароль → подтверждение); **это пока не согласовано** и требует API.
- Отображать сведения о сессии или последнем входе **только если API их реально предоставляет**; не придумывать даты.
- «Выйти» — существующий концептуальный `signOut()`; выход из всех устройств — возможное развитие после согласования API.
- **Не показывать** пользовательские пароли, хеши, токены и строки подключения.

### C. Мой рабочий контекст (только чтение)

- Для владельца и обычного администратора — компания и категория/роль.
- Для Office — компания и разрешённые рабочие функции, если API возвращает их.
- Для Vessel — назначенное судно/суда, если возвращены API; управление привязками выполняет администратор в другом разделе.
- Для суперадмина — «Платформа», без выбора `tenant_db` в личном профиле.

## 4. Матрица действий по ролям

Обозначения: **Да** — согласованное правило; **Предл.** — предложено для согласования; **Нет** — запрещено согласованными правилами; **Открыто** — ещё не решено.

| Действие | Superadmin | Company Owner | Tenant Admin | Office | Vessel |
| --- | --- | --- | --- | --- | --- |
| Смотреть **свой** профиль и роль | Предл. | Предл. | Предл. | Предл. | Предл. |
| Редактировать **своё** отображаемое имя | Предл. | Предл. | Предл. | Предл. | Предл. |
| Сменить **свой** e-mail | Открыто | **Да** | Открыто | Открыто | Открыто |
| Самостоятельно сменить **свой** пароль | Предл. | Предл. | Предл. | Предл. | Предл. |
| Смотреть назначенную компанию/суда (если есть) | Предл. | Предл. | Предл. | Предл. | Предл. |
| Самостоятельно менять роль/компанию/привязки судов | Нет* | Нет | Нет | Нет | Нет |
| Управлять **чужим** аккаунтом владельца в «Моём аккаунте» | Нет | Нет | Нет | Нет | Нет |
| Выйти из сессии | Предл. | Предл. | Предл. | Предл. | Предл. |

*Суперадмин управляет компаниями на отдельном уровне Platform UI; он не переназначает себе компанию из личного профиля.

**Вне этой матрицы, но уже согласовано:** Superadmin в **Platform UI** сбрасывает пароль владельца и вручную заменяет его e-mail. Company Owner в **Company UI** управляет дополнительными администраторами; Tenant Admin — обычными пользователями, судами и данными, но не другими администраторами.

## 5. Сценарии формы и правила интерфейса

### 5.1. Собственная смена e-mail владельцем — согласованный сценарий

1. Company Owner → User Menu → «Мой аккаунт» → поле «E-mail».
2. Ввод нового e-mail; клиент проверяет базовый формат и отсутствие изменений.
3. Кнопка «Сохранить» вызывает **API для собственного аккаунта**, не адрес платформенной карточки другой компании.
4. Сервер подтверждает роль/личность текущей сессии, **глобальную уникальность нового e-mail** и сохраняет адрес **на том же account ID**.
5. При успехе обновить профиль, User Menu и отображаемый адрес входа. **Нет ожидания письма**. При конфликте оставить прежний адрес и показать понятную ошибку. Сессии/повторная проверка доступа определяются API.

### 5.2. Смена e-mail владельца суперадмином — отдельный экран

Platform → Компания → Владелец → «Изменить e-mail» → новый адрес → явное подтверждение действия → API. После успеха обновить карточку компании; UI не «переключает» аккаунт владельца и не выдаёт суперадмину роль владельца.

### 5.3. Редактирование остальных личных полей — проектное предложение

Общий шаблон: открыть → редактировать свои разрешённые поля → проверить формат → сохранить через API → показать результат. Если право или поля не подтверждены API, использовать **read-only**, а не показывать кнопку, которая имитирует сохранение.

### 5.4. Предлагаемые состояния

- Загрузка текущего профиля; пустые необязательные поля; только чтение; процесс сохранения; успешно сохранено; несохранённые изменения при уходе.
- Ошибка валидации; e-mail уже занят глобально; `401` сессия истекла; `403` изменение запрещено; `409` конфликт, если такой формат подтвердит API; `429` ограничение запросов (если API возвращает); ошибка связи/сервиса.
- Сохранение доступно только для изменённых и валидных полей; повторную отправку блокировать до ответа.
- Light/Dark и mobile адаптивность из эталонной дизайн-системы, без новых базовых компонентов.

## 6. Черновик frontend-моделей и сервисов (НЕ утверждённый API)

```ts
type AccountSource = 'platform_users' | 'tenant.auth';
type AccountKind = 'superadmin' | 'company_owner' | 'tenant_admin' | 'office' | 'vessel';

interface MyAccountView {
  userId: string;           // stable, read-only; API знает источник
  accountSource: AccountSource;
  accountKind: AccountKind;  // условное обозначение frontend
  email: string;
  displayName?: string;
  company?: { id: string; name: string };
  assignedVessels?: Array<{ id: string; name: string }>;
  permissions: string[];     // фактические разрешения от API
}

interface AccountService {
  getMyAccount(): Promise<MyAccountView>;
  updateMyDisplayName?(displayName: string): Promise<MyAccountView>; // предложение
  updateMyOwnerEmail?(newEmail: string): Promise<MyAccountView>;     // бизнес-правило подтверждено; контракт не готов
  changeMyPassword?(input: { currentPassword: string; newPassword: string }): Promise<void>; // предложение
}
```

**Не предполагаем прямого доступа к БД** и не считаем эти названия endpoint-ами. Отдельные операции Platform Admin над владельцем определены в [AUTH_AND_ROUTING.md](AUTH_AND_ROUTING.md): концептуальные `setCompanyOwnerEmail` и `requestCompanyOwnerPasswordReset`.

## 7. Открытые продуктовые решения

1. **Может ли каждый пользователь (Superadmin, Tenant Admin, Office, Vessel) самостоятельно менять свой e-mail**, или для них смена доступна лишь через администратора? Для владельца право **уже согласовано**.
2. Разрешаем ли **каждой категории самостоятельно менять свой пароль**, зная текущий пароль? Как выглядит восстановление пароля остальных ролей?
3. Какие профильные поля действительно существуют в API: ФИО/отображаемое имя, телефон, аватар, язык, часовой пояс, последний вход?
4. Какие статусы аккаунта и безопасность смены e-mail подтверждает сервер (переаутентификация, аудит, уведомления, отзыв сессий)?
5. Как API сообщает назначения судов и права, и нужно ли отображать в личном профиле все назначенные суда?
6. Какие действия владельца в собственном профиле отличаются от управления им суперадмином, кроме подтверждённой смены e-mail?

## 8. Граница реализации

**Сейчас только проектирование в `architecture/`.** Не создаём production-маршрут `/account`, API, новые таблицы или mock-страницу в `modules/` до согласования требований. Эталон дизайна и существующее демо остаются неизменными.
