# Monitoring Project — Frontend Architecture

**Статус:** проектирование frontend, версия 0.1 (13.10.2026). Не является схемой БД, утверждённым API или реализованной системой авторизации.

## Зачем этот раздел

Этот каталог — отдельное рабочее пространство для **будущей архитектуры frontend**, независимое от:

- [`docs/DESIGN_SYSTEM_CONSTITUTION.md`](../docs/DESIGN_SYSTEM_CONSTITUTION.md) — эталона дизайна, компонентов и поведения UI;
- [`components/`](../components/) и [`tokens/`](../tokens/) — библиотеки компонентов и дизайн-токенов;
- [`modules/`](../modules/README.md) — действующих **демонстрационных экранов** на mock/localStorage;
- [`docs/PROJECT_ARCHITECTURE.md`](../docs/PROJECT_ARCHITECTURE.md) — исторического плана UI-модулей, который может не отражать новые согласованные правила.

**Демонстрационные экраны зафиксированы:** без отдельного решения не перерабатываем их бизнес-логику, авторизацию, лицензирование, маршруты или визуальную оболочку. Здесь готовим модель для последующей интеграции с API другого отдела.

## Документы

1. [**DECISIONS.md**](DECISIONS.md) — согласованные правила Platform/Tenant, источники пользователей, лицензия vs подписки, границы ответственности; открытые вопросы отделены от решений.
2. [**AUTH_AND_ROUTING.md**](AUTH_AND_ROUTING.md) — модель **единой страницы входа** для пользователей `platform_users` и `tenant.auth`, схема сессии, маршрутизация по контексту и правам, защита маршрутов, состояния UI.
3. [**MY_ACCOUNT.md**](MY_ACCOUNT.md) — черновик единого экрана «Мой аккаунт» для пяти категорий пользователей: поля, матрица самостоятельных действий, отдельные административные операции, состояния UI и предполагаемые интерфейсы сервисов. **Неутверждённые права выделены отдельно.**
4. [**PERMISSIONS_MATRIX.md**](PERMISSIONS_MATRIX.md) — первая итерация матрицы полномочий **Super Admin**: утверждённые ограничения, функции демо, открытые права и порядок согласования остальных операций.
5. [**LICENSING_AND_SUBSCRIPTIONS.md**](LICENSING_AND_SUBSCRIPTIONS.md) — согласованная модель **системной лицензии**, **модульных подписок**, сроков доступа, полномочий Super Admin и заявок Company Owner; платежная интеграция и API-контракты остаются открытыми.
6. [**VESSELS_AND_SCOPES.md**](VESSELS_AND_SCOPES.md) — **единый реестр судов и активная группа**: active/inactive/archived, лимиты модулей и сохранение истории.
7. [**SHIP_PARTICULARS_AND_USER_ASSIGNMENTS.md**](SHIP_PARTICULARS_AND_USER_ASSIGNMENTS.md) — **согласованные Ship Particulars и назначения Office/Vessel**: два обязательных поля, новое судно `inactive`, many-to-many по судам, серверный scope и границы неутверждённого API.
8. [**ETALON_PLATFORM_TENANT.md**](ETALON_PLATFORM_TENANT.md) — **согласованная трёхуровневая модель** `etalon_db → platform_db → tenant_db`, поэтапное развитие эталона, выбор Object Type и разграничение утверждённых принципов и открытых вопросов к VDMS API.
   
Дальше здесь можно добавить `API_CONTRACTS.md`, `MODULE_NAVIGATION.md`, `FRONTEND_DATA_MODELS.md` и `INTEGRATION_CHECKLIST.md` — **после** обсуждения их содержания.

## Правила архитектурного проектирования

- Разрабатываем **только frontend**. Схемы БД, реальные API, авторизационный backend и маршрутизацию физических tenant-баз реализует другой отдел.
- Термины и имена из согласованной модели сохраняем: `etalon_db` (развиваемая эталонная структура Tenant и типы объектов), `platform_db.platform`, `tenant_db_XXXXXX`, `platform_users`, `tenant.auth`, `licenses`, `subscriptions`, `core`, `documents` и остальные модули.
- Разделяем **«Согласовано»**, **«Предлагается frontend»** и **«Требует согласования с API/БД»**. Не превращаем предварительные пути URL, JSON и имена полей в контракт без подтверждения.
- Ни UI, ни API-клиент не подключается к базе данных напрямую и не принимает физическое имя БД как пользовательский параметр доступа.
- Предполагаем сервисы-адаптеры: экраны вызывают один frontend-интерфейс данных, за которым временно могут находиться mock-ответы, а позднее — реальные API.
- Адаптивность, Light/Dark, доступность и компоненты — из утверждённой дизайн-системы; архитектурные документы не создают новую дизайн-систему.
- Каждое новое решение добавляется сюда до реализации. Старые прототипы не объявляются работающими production-экранными маршрутами.

## Предлагаемый порядок дальнейшей работы

1. Согласовать авторизационную модель и маршрутизацию на основе [AUTH_AND_ROUTING.md](AUTH_AND_ROUTING.md).
2. Согласовать с другим отделом операции API, модель сессии, полномочия и ограничения tenant.
3. Описать frontend data models и состояния загрузки/ошибок для каждого модуля.
4. Спроектировать навигацию и App Shell по ролям, используя исходный Dashboard Template.
5. Только после согласования контрактов готовить интеграцию и mock-adapters; текущие страницы `modules/` пока не изменять.

## Версионирование решений

Документ может меняться по ходу обсуждения. Указание **«согласовано»** означает, что принцип явно подтверждён в проектном обсуждении, но **не** означает, что API уже реализован или его формат утверждён.
